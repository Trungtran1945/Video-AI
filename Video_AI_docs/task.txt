### P0/P1 — Quota accounting tính cả cache_hit

backend/src/services/quotaGuardService.js:

getQuotaSnapshot() đang COUNT provider_logs theo:

user
provider
created_date

nhưng không filter status.

backend/src/lib/callProvider.js khi provider cache hit ghi:

status = 'cache_hit'

Do đó:

provider request thật
→ status=ok

cache hit
→ status=cache_hit

có thể bị tính thành 2 quota requests.

Ngoài ra các provider attempt thất bại cũng có thể bị tính tùy status.

Quota accounting phải phản ánh external provider consumption, không phải số lượng application log events.

--------------------------------------------------

### P1 — Daily quota và minute rate limit đang bị gộp

getQuotaSnapshot():

pctDaily = usedToday / limitToday
pctMinute = usedThisMinute / limitThisMinute
percentUsed = max(pctDaily, pctMinute)

Frontend lại hiển thị percentUsed cùng:

usedToday / limitToday

Ví dụ:

daily = 10%
minute = 90%

UI có thể hiển thị:

90% (100/1000)

→ gây hiểu nhầm rằng daily quota đã dùng 90%.

checkQuotaWarning() cũng có message:

"Đã sử dụng XX% quota hôm nay"

dù percentUsed có thể đến từ minute limit.

--------------------------------------------------

### P1/P2 — selectBestApiKey trả snapshot chung cho mọi key

selectBestApiKey(userId, provider):

load active API keys theo priority.

Sau đó:

const snapshot = await getQuotaSnapshot(userId, provider)

và trả snapshot cùng apiKey.

Snapshot hiện là user/provider-level, không phải apiKey-level.

Phải xác định contract rõ ràng.

Nếu quota per user/provider:

đặt tên/contract rõ ràng.

Nếu quota thực sự per key:

thêm apiKeyId vào quota query.

Không để caller hiểu nhầm.

### 4.1. Thiết kế quota accounting contract

Trước khi sửa query, xác định rõ:

- application call;
- provider attempt;
- successful external request;
- rate-limited external request;
- quota-exceeded request;
- cache hit;
- local/mock execution.

Document contract.

Quota usage không được đồng nghĩa đơn giản với:

COUNT(provider_logs).

--------------------------------------------------

### 4.2. Không tính cache_hit là provider consumption

provider_logs:

status='cache_hit'

không được tính là external provider request.

Đặc biệt:

callProvider() có cache hit:

→ provider không được gọi.

Quota snapshot:

→ không tăng.

Bổ sung regression test.

--------------------------------------------------

### 4.3. Xác định status nào được tính quota

Tạo helper hoặc constant duy nhất, ví dụ:

isQuotaCountingProviderLog(status)

Không duplicate danh sách status trong nhiều module.

Chỉ count status thực sự đại diện cho attempt/request đã gửi tới provider.

Nếu semantics provider-specific khác nhau:

document rõ và không giả định sai.

--------------------------------------------------

### 4.4. Tách daily quota và minute rate limit

Không trả một:

percentUsed

duy nhất được tạo bằng max(daily, minute).

Thay vào đó trả:

{
  daily: {
    used,
    limit,
    percent
  },
  minute: {
    used,
    limit,
    percent
  }
}

Có thể giữ các field cũ:

usedToday
limitToday
usedThisMinute
limitThisMinute
percentUsed

nếu cần backward compatibility, nhưng percentUsed phải được định nghĩa rõ hoặc deprecated.

Không để frontend dùng percent minute như daily percent.

--------------------------------------------------

### 4.5. Warning semantics

precheckStage() phải xác định rõ warning:

daily_quota_risk

hay:

minute_rate_limit_risk.

Không gộp thành quota_risk nếu mất semantics.

Nếu warning daily:

estimatedRequests phải vượt daily limit.

Nếu warning minute:

phải dùng window minute tương ứng.

Không warning giả chỉ vì minute utilization cao rồi hiển thị thành daily quota.

--------------------------------------------------

### 4.6. selectBestApiKey contract

Quyết định và document:

quota là per-user/provider
hoặc
quota là per-api-key.

Nếu hiện tại provider limits trong schema là user/provider:

giữ user/provider semantics và đổi tên snapshot rõ ràng.

Ví dụ:

providerQuotaSnapshot

Không gọi nó:

apiKeySnapshot.

Nếu có provider thực sự quota per-key:

bổ sung apiKeyId có kiểm soát.

Không fake per-key quota bằng cách chia quota user cho số key.

--------------------------------------------------

### 4.7. Aggregate quota endpoint

Thay vì frontend gọi:

GET /providers/gemini/quota
GET /providers/openai/quota
GET /providers/elevenlabs/quota

nên cân nhắc thêm:

GET /providers/quota-summary

Endpoint trả tất cả provider cần thiết trong một response.

Ví dụ:

{
  "providers": {
    "gemini": {...},
    "openai": {...},
    "elevenlabs": {...}
  }
}

Chỉ query providers user thực sự cần.

Không expose API keys/secrets.

Giữ endpoint cũ để backward compatibility nếu frontend/API consumers đang sử dụng.

--------------------------------------------------

### 4.8. QuotaBanner

Thay:

apiKeysApi.list()
+
N quota requests

bằng aggregate quota endpoint nếu phù hợp.

Poll mỗi 60 giây vẫn được giữ.

Không probe provider không có active key, trừ khi có lý do product rõ ràng.

Nếu aggregate endpoint chưa thể thêm:

ít nhất cache result client-side và chỉ query providers active.

Cleanup interval khi unmount.

Không tạo duplicate polling khi Layout re-render.

--------------------------------------------------

### 4.9. UI quota semantics

ApiKeys.jsx:

Không hiển thị:

90% quota ngày

nếu 90% thực tế là minute rate.

Hiển thị riêng:

Ngày: 10% (100/1000)
Phút: 90% (9/10)

Nếu một metric không có limit:

hiển thị N/A hoặc bỏ qua.

QuotaBanner phải cảnh báo đúng:

"Rate limit/phút gần đầy"

hoặc:

"Quota ngày gần đầy".

Không dùng message chung gây hiểu nhầm.

--------------------------------------------------

### 4.10. Failover dedupe

providerFailover.js bắt buộc:

normalize
→ providerKey
→ dedupe
→ health ordering
→ maxAttempts.

Không slice trước dedupe.

Bổ sung test:

A:key1
A:key1
B:key2

maxAttempts=2

phải thử A rồi B.

Test thêm:

A:key1
A:key2
B:key3

để chứng minh dedupe theo đúng identity.

--------------------------------------------------

### 4.11. Aggregate provider failure

Thu thập:

provider
errorCode
kind
retryable
attempt

và classify:

ALL_TRANSIENT
ALL_QUOTA
ALL_AUTH
ALL_PERMISSION
ALL_CONFIGURATION
MIXED.

NO_PROVIDER_AVAILABLE vẫn có thể giữ để backward compatibility.

Nhưng:

retryable

phải phản ánh aggregate.

Không dùng first error làm semantics duy nhất.

Frontend error mapping phải tiếp tục hoạt động.

--------------------------------------------------

### 4.12. Retry-After

Giữ parseRetryAfter() hiện có.

Nếu aggregate failure chứa nhiều Retry-After:

chọn policy rõ ràng, ví dụ:

- max retry-after cho ALL_TRANSIENT;
- provider-specific failover trước;
- không retry ngay với ALL_QUOTA.

Không hard-code một giá trị không liên quan.

--------------------------------------------------

### 4.13. REPORT.md

Không coi REPORT.md là runtime evidence nếu SHA không trùng HEAD.

Có thể:

- cập nhật REPORT.md với verified commit SHA;
- hoặc ghi rõ "historical report";
- hoặc thêm generated-at + verified SHA.

Không xóa report nếu repo cần nó, nhưng phải loại bỏ ambiguity.

5. TIÊU CHÍ NGHIỆM THU
==================================================

### Quota accounting

Provider thực:

1 call
→ usage +1.

Cache hit:

→ usage +0.

Local/mock:

→ không tính external provider quota.

Rate limited:

→ được tính theo contract đã document nếu request đã tới provider.

Không có status ambiguity.

--------------------------------------------------

### Daily/minute

Ví dụ:

daily 100/1000
minute 9/10

API phải trả:

daily.percent = 10
minute.percent = 90.

UI không được hiển thị:

90% quota ngày.

Warning phải nói đúng:

minute rate limit.

--------------------------------------------------

### API key semantics

Nếu quota user/provider:

snapshot contract phải nói rõ.

selectBestApiKey không được trả object khiến caller tưởng snapshot là key-specific.

--------------------------------------------------

### QuotaBanner

Một polling cycle:

→ tối đa một aggregate quota request + request cần thiết để biết active providers.

Không:

1 + N quota requests

nếu aggregate endpoint đã được triển khai.

Unmount:

→ interval cleanup.

Multiple renders:

→ không tạo duplicate intervals.

--------------------------------------------------

### Failover

A:key1
A:key1
B:key2

maxAttempts=2

Expected:

A:key1
B:key2.

--------------------------------------------------

### Aggregate error

All transient:

retryable=true.

All quota:

retryable=false hoặc policy phù hợp với retry scheduler, nhưng phải nhất quán và có classification ALL_QUOTA.

Mixed:

classification=MIXED.

--------------------------------------------------

### Backward compatibility

Giữ:

GET /providers/:provider/quota

nếu consumer hiện tại còn dùng.

Không phá:
