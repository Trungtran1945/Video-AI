# TASK-019

## Title
Schedule drainQueued recurring job and trigger queue drain on pipeline finish

## Type
bug

## Priority
high

## Autonomy
auto

## Evidence
[backend/server.js:106-112](file:///D:/E/Video_AI/backend/server.js#L106-L112) imports and starts `drainQueuedWorker`, which listens to BullMQ queue `'drain-queued'`. However, no BullMQ queue for `'drain-queued'` exists (only `cleanupQueue`, `notifyQueue`, and `projectQueue`), no repeatable job is added in `server.js` (unlike `cleanupQueue.add('sweep', ..., { repeat: ... })`), and [backend/src/pipeline/runner.js:567-618](file:///D:/E/Video_AI/backend/src/pipeline/runner.js#L567-L618) does not trigger draining when a pipeline run completes or fails. Furthermore, [backend/src/queue/workers/drainQueued.js:57-62](file:///D:/E/Video_AI/backend/src/queue/workers/drainQueued.js#L57-L62) calls `queryOne` for `SELECT user_id, COUNT(*) as cnt FROM projects WHERE status = 'queued' GROUP BY user_id`, only processing the first user and starving all subsequent users.

## Affected Areas
- `backend/server.js`
- `backend/src/queue/workers/drainQueued.js`
- `backend/src/pipeline/runner.js`

## Expected Outcome
1. Export a `drainQueue` BullMQ Queue instance for `'drain-queued'`.
2. Schedule a repeatable drain job (every 60 seconds) in `server.js` when Redis is ready.
3. In `drainQueued.js`, replace `queryOne` with `query` for the grouped user query to prevent multi-user starvation.
4. When `runPipeline` completes or fails in `runner.js`, trigger a job in `drainQueue` (if Redis is available) to immediately consume the next queued project.

## Constraints
Maintain graceful degradation when Redis is unavailable.

## Suggested Verification
`cd backend && node -e "import('./src/queue/workers/drainQueued.js')"`

# TASK-021

## Title
Clean up abort event listener in media ffmpeg runner on child process exit

## Type
bug

## Priority
medium

## Autonomy
auto

## Evidence
[backend/src/media/ffmpeg.js:63-81](file:///D:/E/Video_AI/backend/src/media/ffmpeg.js#L63-L81): In `runBin()`, when an `AbortSignal` is supplied, `signal.addEventListener('abort', onAbort, { once: true })` registers an abort handler on the signal. When the child process exits normally or errors out (`child.on('close')`, `child.on('error')`), `signal.removeEventListener('abort', onAbort)` is never called. Because a single pipeline run reuses the same `AbortSignal` across multiple FFmpeg and FFprobe calls, listeners accumulate and cause memory leaks and Node.js `MaxListenersExceededWarning`.

## Affected Areas
- `backend/src/media/ffmpeg.js`

## Expected Outcome
`signal.removeEventListener('abort', onAbort)` is called whenever `runBin()` settles (in `close`, `error`, and timeout handlers) ensuring no dangling listeners remain on the signal.

## Constraints
Do not alter SIGTERM/SIGKILL escalation logic or cancel rejection behavior.

## Suggested Verification
`cd backend && node -e "import('./src/media/ffmpeg.js')"`
